## 四、多 Agent 的提升体现在哪

1. **独立验证抓到了实现者没意识到的问题**。Bug 修复的 codex 发现测试没覆盖的 `10.075` 半分边界并补了回归测试；claude-acp 复核指出 `WeakMap` 锁只在单进程、同一对象引用下有效，多 worker/多实例仍会超卖——这是单 Agent 那轮完全没有的视角。
2. **角色分离让验收更可信**。三个只读步骤都明确“不要修改文件”，结论写在报告里，不会为了全绿而弱化测试。
3. **失败可以局部处理**。游戏和看板第 1 步撞回合上限时，跳过该步让第 2 步“验收收尾”接手，不需要抛弃整条任务重来。
4. **并行确实缩短总墙钟**。四个项目约 2 小时内全部跑完，其中数据分析 1 小时、Bug 修复 30 分钟。

## 五、代价与不足

1. **协同开销明显**。四个计划合计约 15.7M token，大头是 codex 的长上下文（单步 3.4M–5.8M）。codex 单步实际用量超过 200 万预算上限，说明预算只在启动前检查，长跑无法中途止损。
2. **回合上限成为大任务瓶颈**。60 回合仍不足以完成“从零写游戏/看板 + 测试 + 文档”，两次都只能跳过实现步骤让验收步骤收尾。
3. **依赖链是单点**。第 1 步失败会阻塞后两步；恢复只能重试或跳过。
4. **重启丢进度**。服务重启会把运行中的工单标记为失败，不尝试续接已有 CLI 会话。
5. **评审结论有时只落在报告附件里**：已修复，CLI 执行器没有结构化摘要时会回退到报告正文，工单摘要不再只显示“CLI执行完成”。

## 六、本轮修复的产品问题

1. 并发满退回 `waiting` 的计划步骤，名额释放后自动推进（跨计划唤醒）。
2. 重试可带 `maxTurns` 补回合预算（上限 60）。
3. `launchStep` 失败回写改用 `privateTicket`，不再抹掉 `command` / `executorInput`。
4. 补齐审批预览、策略规则、工单状态机的内层目录（结构整理 Phase 1–2，见 `docs/structure-inventory.md`）。
5. 本轮之前已修：孤立 queued 工单重入队、项目页导航被最近工单抢占、CLI 默认回合数统一、失败会话保留 sessionId、完全权限映射 `--dangerously-skip-permissions`。
6. CLI/ACP 工单摘要回退：执行器没有 `artifacts.cli.summary` 时使用 `report.summary`，评审结论不再只剩“CLI执行完成”。

全量单测 **922/922 通过**；`npm run lint:arch` 通过。

## 七、仍建议修复

- ~~执行器自身 `maxConcurrent=2` 写死~~：已改为引擎在策略变化时下发 `setConcurrency`（CLI 执行器支持 1–16），`npm test` 921/921 通过。
- ~~`maxTurns` 上限 60 对大任务偏低~~：已提到 120；Claude Code 默认回合数已提高到 60（Codex 仍为 30），可由 `LAGENT_CLI_MAX_TURNS` 或调用方指定。可写提示词也明确要求优先用测试/构建验证，不要自启开发服务器或浏览器，避免回合耗在自检上。
- Token 预算只在启动前检查，长跑可大幅超支；建议加运行中的阈值中止。
- 服务重启后优先用已保存的 CLI `sessionId` 续接，而不是直接判失败。
- ~~claude-acp 的最终文本应同步到工单摘要~~：已改为 `artifacts.cli.summary` 缺失时回退到 `report.summary`，并补了回归测试。

## 八、结论

多 Agent 的定位成立：它提升的是**验收质量与问题发现率**，不是原始生成速度。实现→验证→评审三段式在 Bug 修复和看板项目上抓到了单 Agent 漏掉的真实缺陷；但回合上限、预算控制和重启恢复仍是瓶颈。最有效的用法是给每个步骤明确范围和小预算，失败时用跳过/重试局部处理，而不是让一个 Agent 一口气做完整项目。
