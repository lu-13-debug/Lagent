## 参考范围与事实

MODEX目录是安装后的Electron应用。实际阅读了 resources/app/templates 下 README、RESEARCH_CONTRACT_TEMPLATE、EXPERIMENT_PLAN_TEMPLATE、EXPERIMENT_LOG_TEMPLATE、NARRATIVE_REPORT_TEMPLATE、FINDINGS_TEMPLATE，以及 tools/skill_instruction_guard.py、watchdog.py 的可读部分。

核心 workflow_engine、skill_capsule 等是编译模块；目录结构只能说明模块划分，不能证明其内部实现。不反编译，不复制实现代码，不搬运runtime或用户数据库。以下借鉴是根据可读材料提炼的设计，不宣称复刻其引擎。

| MODEX可读材料 | 实际体现的机制 | Lagent拟采用方式 |
| --- | --- | --- |
| RESEARCH_CONTRACT_TEMPLATE.md | 当前选定问题、范围、依据、状态；恢复时不加载全部候选方向 | 分析契约：业务问题、指标定义、比较范围、非目标、数据版本、预算 |

## 现有代码的具体不足

1. server/workflow-config.js 为13阶段写了不同指令，但 inputSchema/outputSchema基本共用 summary/operations/findings，缺乏阶段专有的可检验交付物。
2. server/stage-agent.js 的 previous仅传摘要。分析计划即使写出依赖与比较设计，也没有成为后续工具和报告必须遵循的结构化输入。
3. stageFacts对daily截90行、channels取前40、retention取40行，未向模型声明抽样覆盖。报告仍可能泛称全量结论。
4. 数据处理目前只预览；没有持久派生数据版本，也没有以输入版本判断阶段缓存有效性的机制。
5. 分支固定执行，分析模板主要是目标文字。版本/活动复盘虽要求补充日期，但没有可执行、可核验的比较计划。
6. 数字核验当前主要检查是否出现在facts中，不能确认它属于哪个指标、分母或时间窗口；不应把“某处存在同样数字”视为证据匹配。
7. 核验失败直接终止，缺少只回到有问题产物的有限修订；恢复新任务也未完整复用AI阶段结果。
8. Skill内容偏通用；现有领域注册与指标依赖应该真正参与Skill编排，避免所有领域沿用游戏描述。

## 三条路线

| 路线 | 内容 | 取舍 |
| --- | --- | --- |
| A：只优化Skill文本 | 扩充角色、检查清单、示例和说明 | 改动小，但无法解决摘要交接、恢复与证据归属 |
| B：阶段合同与证据闭环（推荐） | 保留现有设置和节点ID，新增结构化产物、按需路由、有限修订和版本恢复 | 可逐步验收，直接改善真实执行质量 |
| C：重建通用编排平台 | 自由DAG、任意插件、复杂循环和并发调度 | 范围大，暂不适合当前产品规模 |

## 推荐B：先优化现有阶段

| 现有板块 | 新交付物 | 必须检查的内容 |
| --- | --- | --- |
| 数据理解/质量 | DataProfile、阻断项和可分析能力表 | 字段含义、缺表、时区、观察窗口、币种、覆盖声明 |
| 分析计划 | AnalysisContract、AnalysisPlan | 问题、非目标、口径、所需证据、阶段依赖、预算、确认项 |
| 数据处理 | TransformPlan、TransformReceipt | 规则、前后行数、变化范围、原数据引用；需确认的规则不执行 |
| 活跃/留存/商业化/渠道/周内 | AnalysisResult | metricId、值、单位、分母、期间、数据版本、证据ID、局限 |
| 绘图 | FigurePlan、FigureReceipt | 图回答什么问题、数据源、轴单位、范围、缺失值、图注、与证据对应 |
| 洞察 | FindingsLedger | 事实/推断/假设/建议分开，证据引用、反例和不确定性 |
| 报告 | ReportDocument | 段落与图表引用有效证据，不自行重新计算指标或补充未知数字 |
| 核验 | ReviewReceipt | 规则检查和AI审阅分开；定位到节点/产物/字段，区分阻断与提示 |
| PDF | ExportReceipt | 内容版本、实际渲染文件、字体、页数、生成状态；禁止用旧PDF冒充新版本成功 |

这些交付物是JSON数据合同，Markdown只作为阅读视图。校验由服务端执行，不能只把schema写入提示词。

## 补充能力：有条件启用，不强制增加付费节点

1. **指标口径确认**：嵌入计划阶段，锁定分母、去重、时区、退款和观察窗口。
2. **前后期/分组比较**：必须具备比较时间、可比指标和覆盖信息；输出绝对差、相对差与不可比原因。没有对照组不能认定因果。
3. **异常与稳健性检查**：按数据量启用描述性异常、极值影响、窗口变化敏感性；显著性检验需要方法适用条件与样本依据，不强行添加p值。
4. **图表审阅**：作为绘图阶段的规则检查，检查轴、单位、范围和数据一致性，不默认增加第二个模型调用。
5. **有限修订**：核验指出哪个产物有问题，就只修订该产物及依赖它的下游；第一版最多2轮。改口径/删行/填补依然等待用户明确确认。
6. **结果复用**：仅复用输入数据版本、分析契约、Skill hash、模型参数、工具版本和上游产物hash全部匹配且已校验的产物。范围变化只使受影响分支及下游失效。

缺数据或不适用的节点记录skipped/not_applicable及原因。预算不足记录未完成检查，不声称通过；不自动换更便宜的模型。

## Skill组织与上下文

内置Skill拆成职责说明、输入合同、操作步骤、工具权限、输出合同、成功/失败标准、正反例和小型评估样例。系统规则、领域指标规则、任务数据和用户私人Skill分层装配；私人Skill不能覆盖指标口径和工具权限。版本变化保留旧任务冻结版本。

上下文只加载当前AnalysisContract、必要上游结构化产物和FindingsLedger。大表使用可追溯聚合及按ID读取工具，显式返回总行数、已提供行数、抽样方法和覆盖范围，避免静默截断。报告和核验读取当前有效产物，旧版本记录保留但不能混入当前证据。

不将内部schema/证据字段名直接塞进报告正文。页面展示用户可理解的阶段产物、待确认问题、核验结论和预算消耗。

## 实施顺序与验收

### 第一批：合同、Skill和证据

增加阶段专有schema与运行时验证；升级内置Skill及领域规则装配；计划变成真实可消费的产物；增加结构化数值证据和上下文覆盖声明。旧阶段ID与私人Skill版本保留，旧输出以legacy适配读取，不宣称满足新合同。用户无需重新输入凭据。

验证：缺字段/错误单位/引用错期间或分母会被拒绝；计划要求的分析能在下游产物中找到；未知字段不进入模型；旧任务仍可读；抽样必须显式披露。

### 第二批：按需分析和有限修订

根据目标与数据能力启用比较、异常和敏感性检查；生成真实图表计划；核验定位到产物，最多2轮定向修订。现有每阶段模型和强度设置继续有效；新增能力默认继承所属阶段配置。

验证：缺对照时不输出因果，覆盖不一致不计算伪增长；绘图数据/单位匹配；修订不重复执行无关付费阶段，达到上限后明确未通过。

### 第三批：派生数据与恢复

标准化规则生成版本化派生数据和处理回执，原数据保留。增加内容hash和上游依赖登记，使恢复只重跑失效部分；模型调用未知结果不得当作已成功缓存。确认项与额度仍遵循当前服务端规则。

验证：原数据未修改；转换前后差异可核验；换Skill/数据/范围只使正确下游失效；取消/重启/模型失败不产生重复结算；双账号产物和恢复权限隔离。
